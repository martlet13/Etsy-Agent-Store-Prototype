# Build notes — Claude-assisted build session

This documents what was added to the prototype in one build pass, so it's
clear what's real, what's still a stub, and what only you can finish
(since it needs your own accounts and runs on your own machine).

## What's real and working now

1. **Claude as an LLM backend** (`_core/llm_backend.py`)
   Every room-agent runner (`run_nova.py`, `run_forge.py`,
   `run_scribe.py`, `run_sentinel.py`, `run_ledger.py`,
   `run_strategist.py`, `run_smith.py`, `run_signal.py`, `run_echo.py`,
   `run_command.py`, `run_archivist.py`, `run_overseer.py`) was refactored
   off a hardcoded local Ollama call onto a shared dispatcher that calls
   the real Anthropic Messages API when `ANTHROPIC_API_KEY` is set
   (`--backend claude|ollama` to force one). This replaces the PRD's
   "automate a ChatGPT web session" approach with a supported, ToS-clean
   API call, made directly from your machine with your own key.

2. **Etsy Open API v3 client, draft-only** (`_core/etsy_api_client.py`,
   `_core/run_etsy_oauth_setup.py`, `create_etsy_draft.py`)
   A real OAuth2 PKCE flow (with a local loopback callback server),
   encrypted local token storage, and calls to create a draft listing,
   upload its image, and read shop sections/taxonomy/shipping
   profiles/return policies. Wired into `publishing_dock.py` as
   `create_etsy_draft_listing()`, gated on: the `etsy` connector being
   explicitly approved (`set_api_connector_approval.py`) AND an explicit
   `--i-approve-this-live-etsy-action` flag on the call itself. There is
   no function anywhere that activates a listing — that step is yours to
   do in Etsy Seller Manager.

3. **Claude-generated Etsy listing copy** (`_core/run_scribe_on_design.py`)
   Title/description/tags are now generated by prompting Claude (or
   Ollama) with the design's concept and safety notes, constrained to
   Etsy's field limits (140-char title, ≤13 tags of ≤20 chars). If the
   LLM call fails or no backend is configured, it automatically falls
   back to the original deterministic template so the pipeline never
   hard-stops.

4. **End-to-end wiring verified** — evidence card → opportunity card →
   design package → Ledger PASS → Scribe listing copy → publish package →
   (gated) Etsy draft create. This chain was exercised locally with
   seeded state and confirmed to correctly block the live Etsy call
   until the connector is approved, and to succeed once it is.

## What you still need to do yourself (by design — see PRD principles)

- Get your own `ANTHROPIC_API_KEY` if you want Claude instead of Ollama.
- Create your own Etsy app, run `run_etsy_oauth_setup.py`, and approve
  the `etsy` connector. Nobody but you can do this — it's your shop.
- Look up your own taxonomy ID / shipping profile ID / return policy ID
  / shop section ID for each listing (helpers are provided in
  `etsy_api_client.py`; there's no UI for this yet, it's a Python call).
- Image generation itself still goes through the existing
  `openai_image_provider.py` (OpenAI Images) — Claude's API doesn't
  generate images, so that pillar wasn't touched. If you want Claude to
  *direct* the image (write the prompt spec) while another provider
  renders it, that's already how `forge_image_kernel.py` is structured;
  only `run_forge.py`'s creative-writing step now goes through Claude.

## Known limitations of this pass

- No UI wiring yet — the new Etsy/Claude functionality is CLI-only
  (`create_etsy_draft.py`, `run_etsy_oauth_setup.py`,
  `--backend`/`--claude-model` flags). The React dashboard in `ui/`
  wasn't touched.
- `create_etsy_draft_listing()` assumes you already know the taxonomy ID
  etc. for a listing; there's no interactive picker.
- The Etsy client has basic 429 backoff but no queueing/pacing across
  multiple drafts in one run (PRD requirement `P-8`) — space out calls
  yourself if you're creating several drafts back to back.
